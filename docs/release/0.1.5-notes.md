# Circuit 0.1.5 Notes

Date: 2026-07-31

Circuit 0.1.5 is a hardening release for the two flows that do the most
work. Fix and Build each had a way to fail or stall on an ordinary
project, and every one of them was found by running the flows for real
rather than by reading the code. There is also a new first-run path.
There are no breaking changes.

## New: `circuit demo` gives a first run something to prove

A first Circuit run should end with something you can check yourself: a
command that failed before the run and passes after it. The old first-run
path could not promise that, because it pointed a new user at their own
repository, where the scope is unbounded and the safest flow to suggest is
the one that demonstrates the least.

`circuit demo` brings its own subject. It scaffolds a throwaway git project
with one real bug and a test that fails because of it, then runs Fix
against that project at the low dial. Nothing is replayed or stubbed: a
real connector, a real model, a real proof chain. The run ends with the
demo project's own test suite going from one failing to two passing, and
you can run it yourself.

## Fixed: a run aimed at another directory wrote its evidence in the wrong place

Aiming a run at a project other than the current directory was a path
nothing had exercised. The default run folder was derived from the working
directory while everything else in the same code path used the project
root. Those agree for a plain `circuit run`, so the discrepancy had never
surfaced. The first live demo run made it visible in the worst way, writing
its entire run folder into the operator's own checkout while reporting that
it had touched nothing outside the demo project. The run folder now follows
the project root. A call that names neither resolves to the working
directory exactly as before.

## Fixed: Build and Fix no longer require an npm project

Build and Fix refuse to claim a change works without running something that
proves it, and the only place they looked was package.json scripts. Every
Python, Go, Rust, Elixir, or Makefile project therefore hit a hard block at
the first step of the two flows that matter most, with a message about a
package.json it was never going to have.

The project config now takes an optional `verification` block:

```yaml
verification:
  general: {argv: [pytest, -q]}
```

Keys are `general`, `build`, and `lint`, and each entry takes `argv`, an
optional project-relative `cwd`, and an optional `timeout_ms`, because a Rust
or Go suite can legitimately outrun the shared budget. Precedence runs from
an inline "verify with `cmd`" in the goal, then config, then package.json
scripts, and it resolves per need, so a Node project can override lint alone
and still get `npm run build` from its scripts. `circuit doctor` now reports
which command Build and Fix would use, or says plainly that there is none
and names the key that fixes it.

## Fixed: a Fix that worked no longer closes short of `fixed`

Two separate causes, both of them the common path rather than an edge case.

A Fix run whose repair landed, whose verification passed, whose change set
was clean, and whose reviewer accepted still closed `partial` and exited 1,
because no regression proof was captured. The frame step is read-only, so it
honestly defers authoring a regression test, and the baseline step inherited
that deferral and ran nothing. It had something to run the whole time: the
brief carries verification commands Circuit resolved from the project itself.
The baseline now runs the first of those before the repair. Red before and
green after is the evidence a person would accept.

A check that was already green before the fix is now recorded as a different
thing from a declared repro that turned out to be wrong. The first is
ordinary for any bug the project's suite never covered and only denies the
`fixed` claim; the second still routes to recovery. When a run does close
short for want of proof, the close reason now says so, instead of leaving
the operator to read reports to discover that evidence was the only
shortfall.

Separately, a run that started in a tree with uncommitted changes from
earlier work could abort even when the repair worked. The implementer reads
the tree, sees a file already modified, takes it for its own, and declares
it; the file's content never moves during the run, so the change set called
the declaration missing and failed the run. A declared path that was already
dirty at run start and is byte-identical now is recorded as pre-existing
dirt. The overclaim gate keeps its teeth: a declared path that was never
dirty and is still clean is still a hard failure, and the allowance applies
only to a run that changed at least one file.

## Fixed: a relaunched Build implementer is told what went wrong

Both routes that re-enter Build's act step after work has been judged
relaunched the implementer with the brief and the plan only. The common one
is a retry after a failing verification: the worker was told to try again
but never told what failed, so a rework attempt could only guess. Fix already
carried this repair; Build has it now.

## Also in this release

The rule for which tests run in the serial stage is now stated rather than
inherited from a list of filenames: a test belongs there if it asserts on
real process timing. Two more files moved under that rule, which removes a
class of false red on `npm run verify`.
