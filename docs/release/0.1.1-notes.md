# Circuit 0.1.1 Notes

Date: 2026-07-15

Circuit 0.1.1 is a fix release with three repairs. If you installed the
CLI from npm with `npm install -g @petepetrash/circuit`, upgrade: write
flows (fix, build) could not complete their first git-state capture on a
0.1.0 npm install. Plugin installs and source checkouts were not affected
by that failure, but every install benefits from the other two repairs:
Fix retries now see why the previous attempt failed, and the progress
stream no longer reports failed checks or stopped runs as successes.

## Fixed: write flows failed on npm installs

The engine captures git state through a small helper script before any
step that writes files. The 0.1.0 package spawned the TypeScript source
of that helper, and Node refuses to type-strip `.ts` files that live
under `node_modules`. The first capture died with
`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, which took fix and build
down with it.

The helper now runs from its compiled `.js` form in installed packages
and falls back to the source form only in source-tree runs. The plugin
runtime bundles ship the compiled helper too.

The release gate grew with the fix: the packed-tarball check now
installs the package into a real `node_modules` layout and executes the
git-state helper exactly the way the verification runtime spawns it, so
this class of failure cannot ship again.

## Fixed: Fix retries could not see why the last attempt failed

When a Fix run's verification or review rejected an attempt, the retry
started over with only the original brief and diagnosis. The worker had
no way to learn what failed, so retries burned budget repeating the same
mistake. This surfaced in a live run where a reviewer rejected a change
twice and neither rework attempt ever saw the reviewer's findings.

Fix's rework step now receives the failure evidence from the attempt
before it: the verification output, the declared change set, the
regression rerun, and the review report, whichever exist. Change-set
accounting also unions files across attempts instead of replacing them,
so a retry no longer fails bookkeeping on files an earlier attempt
already changed.

## Fixed: the progress stream misreported failures as successes

Two honesty bugs in the live progress stream. A step whose check failed
streamed the same "Finished ..." success line as a passing step, so a
failed verification and its retry were invisible. A run that closed
without completing streamed "Finished <flow>." with a success tone as
its final line, directly contradicting the run's own receipt.

Failed checks now stream a visible warning that names the step, the
attempt, and the move the run is taking ("Verify the fix did not pass
on attempt 1; trying again."). Runs that close without completing now
stream an honest final line ("Stopped Fix: ..." with the recorded
reason) with a warning tone. Hosts that follow the rendering contract
show both without any changes.

Related polish in the same release: every fix step now has its own
progress label. Five steps used to render the same "Checking the
work..." line, so an operator could not tell which check was running
or that a retry had re-entered one of them.

## Release process

This release followed the standing runbook
([docs/release/runbook.md](runbook.md)), including the first-run
container lab before the version bump and again after publishing.

## Checks

The standard release gates apply: `npm run verify`,
`npm run check-release-ready`, and the publish gate suite in
`npm run publish:plugins:release`.
