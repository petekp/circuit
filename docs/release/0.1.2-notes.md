# Circuit 0.1.2 Notes

Date: 2026-07-29

Circuit 0.1.2 is a reliability release with one theme: stop losing runs.
An audit of every recorded run found that most lost runs died the same
way. The engine had exactly one answer when something went wrong mid-run:
abort and discard everything, including finished, verified work. This
release gives it better answers. There are no breaking changes; every
install benefits.

## Changed: a spent retry budget no longer throws the run away

When a verification step failed and its retries ran out, the engine
aborted the run and discarded every finished step. In the run corpus this
was the single most common way to lose a run, and the most common trigger
was ordinary: code that fails a check while being worked on.

A step can now declare where exhaustion goes. Verification steps in
Build, Fix, Pursue, and cross-tool-build declare a forward route, so a
spent budget advances to close: the failing report is recorded as
evidence and the run closes stopped, with the work preserved on disk. A
rerouted run can never close as success; the floor is pinned by a
contract invariant. Steps that declare nothing keep the old abort.

## Fixed: a crashed worker no longer kills the run

Circuit does its work by spawning a worker CLI. When that process died (a
crash, a signal, an inactivity timeout) rather than answering wrong, the
engine treated it like failed work. Most steps have no route for that, so
one crash aborted the run. A live review run lost a slice of its target
exactly this way: the CLI stopped after forty-five seconds of real work
and the run never asked again.

A dead worker now gets one spaced re-ask at the connector layer before
anything else reacts. The re-ask does not consume the step's retry
budget, which stays sized for real work failures. Every ask is recorded
in the trace, so the run's history still shows the crash.

Two engine bugs surfaced by this work are fixed with it: a re-asked
worker's earlier crash was attributed to the wrong attempt, and a
retried branch in a fan-out wrote duplicate ids into the run trace,
which corrupted the whole recording and made the run invisible to every
listing.

## Fixed: runs waiting on you were invisible

A run that pauses at a checkpoint waits for an operator decision. Nothing
listed those runs. Five of them had been waiting seventy days with paid
work inside, absent from every tally because a parked run has no result
file yet.

Bare `circuit runs` now lists runs stalled on an operator decision,
including runs recorded by older engine versions, so waiting work is
visible the moment you look.

## Fixed: aborted runs now say why they died

The summary of an aborted run led with a generic line about evidence. The
actual reason was buried in the run folder. The summary headline now
quotes why the run died, and the next-action line tells you to address
that reason before rerunning.

## Fixed: reviews that found issues were filed as failed runs

A review that ends with findings is a healthy run doing its job. Run
history filed it as a failure, because a stopped run was collapsed into
the failure bucket in the history projection. Stopped is now a
first-class outcome through history, the run envelope, and the gate, so
a review with findings reads as needing follow-up, not as broken.

Two smaller review repairs ride along: each unit of a split review now
carries only the warnings for files it actually held, and internal
warning identifiers no longer leak into reviewer prompts or reports.

## Noted openly: the Codex end-to-end proof has not run

A release gate added after 0.1.1 asks for a full paid first-run proof of
the Codex plugin on a fresh host before the public tag moves. The
tooling for that proof is not built yet. This release records that gap
as an approved exception in the release ledgers instead of skipping it
silently.

The free half did run and passed at the exact release candidate: on a
clean host, the plugin installed from a local pack and from GitHub,
Codex discovered all six Circuit tools without any shell fallback, and
the installed plugin tree matched the candidate digest byte for byte.
Both outcome files are recorded under
`docs/release/proofs/runs/codex-mcp-first-run/`. The README keeps
steering sandboxed Codex work to the checkout until the full proof
lands.

## Release process

This release followed the standing runbook
([docs/release/runbook.md](runbook.md)), including the first-run
container lab before the version bump and again after publishing.

## Checks

The standard release gates apply: `npm run verify`,
`npm run check-release-ready`, and the publish gate suite in
`npm run publish:plugins:release`.
