Circuit — how the layers fit together

Circuit is a process compiler and evidence recorder. You author a flow as a fixed plan; it compiles that plan into a surface the host can run; at run time an engine walks the plan step by step, hands each unit of real work to a worker, and records typed evidence. Circuit decides the process and checks the result. The worker writes the code.

LAYER 5RUNTIME ENGINE
Walk the graph, gate each result, record everything
The engine parses the compiled flow into an executable graph, then walks it: run a step, read the route it returns, look up where that route goes, advance. A check gates each advance. Failures take a bounded recovery route; otherwise the run hits a terminal. The engine is generic — it knows nothing flow-specific.

LAYER 6WORKER
Where the actual coding happens
A relay step (and fanout / sub-run branches) hands a prompt to a worker connector and waits. The worker is Claude Code, Codex, or Cursor. It does the thinking and the file edits, then returns a typed result with a verdict.

The engine waits on one worker per relay. Parallel branches (fanout) get isolated git worktrees so they cannot collide.

LAYER 7EVIDENCE
Every decision leaves a typed record
As it runs, the engine appends to an trace and writes typed reports into the run folder. A projection turns those into the operator summary you read at the end. This is what makes a run auditable rather than a black box.

Inside one step — the engine's heartbeat

Execute
Run the step by its kind: a worker relay, a compose, a verification, a checkpoint, a fanout, or a child sub-run.
→
Produce
The step emits a typed report and a verdict string.
→
Check (the gate)
The engine evaluates the result against the step's check. This is the only thing that decides whether the run advances.
✓ pass → continue
Follow the continue route to the next step. Advance.
✗ fail → recover
Take a declared recovery route. Bounded by max_attempts (1, or 2 on recovery). Retry carries the failure as feedback.
■ fail → terminal
If unrecoverable: @stop, @handoff, or @escalate to you.
The catch: for a judgment step, the check only confirms the verdict is a legal value, not that it is true. A false "pass" advances and skips all recovery. (This is the gap the verification-gates note targets.)

Three layers of safety (often confused for one)

1 · Detect

Decide pass vs fail for a step's result.

Has: 4 check kinds + acceptance criteria.

Gap: a model judgment is checked for being a legal value, not a true one. A false pass is invisible here.

2 · Recover

React once a failure is detected.

Has: recovery routes, bounded retries, retry-with-feedback, stop / handoff / escalate.

Gap: retries re-run at the same strength; they add feedback, not a stronger worker.

3 · Chain

Move work to another flow.

Has: sub-run (child flows), the autonomous continuation loop.

Gap: cannot fan out over a discovered work-list of any size, or loop-until-converged, as a general step.

Recovery and chaining are real and solid. Both open ideas sit upstream of them: make the detection trustworthy, and let the chain scale to the work.
