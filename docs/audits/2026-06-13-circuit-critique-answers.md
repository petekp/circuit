# Circuit Sharpening Audit

The single hardest truth this audit surfaced is small and structural: Circuit's one and only committed Fix proof, the artifact a buyer would inspect, is a synthetic fixture whose "fix" echoes its own prompt, whose verification is `node -e process.exit(0)`, and whose independent review never ran (the connector failed) yet whose operator summary still reads "Verification: passed." and whose top-level result reads outcome "complete." A product whose entire pitch is "we don't fabricate a clean result" reproduces a false "done" inside its own proof corpus. The value that the eval data does support is real but narrow: at the same model Circuit does not fix more bugs, it claims fewer false ones, and even that honesty win currently rests on one or two flipped cells out of twelve and has never been measured at the models real users run or against a real per-task dollar cost.

## What Circuit is (WI-*)

### WI-1 - Are the committed release proofs buyer-inspectable evidence of real work?

**Steelman of the concern:** A buyer reaches for the one artifact the vendor controls and points at as proof. If every Fix proof there is a golden fixture whose "bug" is a string-echo, whose verification is a no-op that always exits 0, and whose change-set is two all-zero SHAs over a fabricated `src/login.ts`, then these prove only that the run-folder shape is well-formed. Worse, the operator surface launders this: the summary reads "Verification: passed" and the top-level result reads "complete" while the backing report says "partial" with review "skipped" because the reviewer connector failed. A buyer would believe a real, reviewed fix happened when none did.

**Sober verdict:** Factually correct about the named proof set. The bug is synthetic (`docs/release/proofs/runs/fix/run/reports/fix/brief.json:2`, scope "Synthetic Fix proof fixture." at :5), the verification command is argv `['node','-e','process.exit(0)']` (`verification.json:5`), the change-set SHAs are all-zeros over a fabricated file (`change-set.json:4`), and the index itself declares the scenario "Uses a synthetic bug fixture" (`docs/release/proofs/index.yaml:115`). The backing result records outcome "partial", review_status "skipped" (`fix-result.json:3`), yet the operator summary shows only "Verification: passed" (`operator-summary.md:6`) and the top-level result reports outcome "complete" / "Done: fix completed with required process evidence" (`result.json:18`). Real-bug evidence with genuine failing tests does exist, but under `evals/` not the proofs (`evals/fix-vs-vanilla/tasks/discovery-amount-cents/task.json:7`; `evals/fix-vs-vanilla/results/2026-06-12T15-49-10-758Z-held-out/tasks/heldout-wrap-index/rep-01/summary.json:9`), and those are single-function throwaway fixtures, not real repos.

**Where this is bad for Circuit:** The headline proof set a buyer inspects contains zero real-bug runs, and the operator-facing summary misrepresents the one synthetic run it does ship: a skipped review and a "partial" outcome surface to the operator as a clean "complete / Verification: passed." That is exactly the false-done the product claims to prevent, reproduced inside its own committed proof. The real-bug evidence that exists is not wired into the proofs and is itself synthetic micro-bugs.

**Class / confidence:** confirmed / high

### WI-2 - Routing is model-only; what does Circuit own in the outcome vs the bare model?

**Steelman of the concern:** The first decision a user delegates to a "router" is which flow runs, and Circuit does not make it. The router either accepts a passed flow name (source hardcoded to 'explicit') or throws; its own comment says "there is no deterministic classifier to guess one from the goal text." routed_by/router_reason are constants. If selection is the model's, calling the product a router that "routes work" oversells a logging step. And at the only model-isolated measurement, Circuit does NOT fix more bugs than the bare model (objective-fixed 0.50 in both arms), so it cannot claim a capability edge to offset the routing claim.

**Sober verdict:** The mechanical claim is true exactly as stated. Flow selection is model-only (`src/cli/run.ts:307-320`, with the no-classifier comment at :315-316), routed_by is the literal 'explicit' (`src/cli/run-output.ts:6`), and router_reason is a fixed placeholder (`src/commands/run.md:149-151`). The proof echoes this verbatim (`docs/release/proofs/runs/fix/result.json:11-12`). But the real test is the outcome delta: at the one model-isolated control (both arms Haiku) the flow does NOT fix more bugs (objective-fixed 0.50 both arms) yet cuts false-fixed from 0.500 to 0.333 (`docs/audits/2026-06-11-eval-heldout-hardening.md:295-307`). The charter says it plainly: "at the same model it does not fix more bugs than a bare agent. It claims fewer false fixes" (`docs/evals/theses-and-hypotheses.md:42-46`). So against the named baseline, Circuit's value is not routing and not raw capability; it is a structured verify-and-report loop that lowers the rate of confidently-wrong "done" claims at equal fix rate. The catch: the only committed full-loop demonstration is synthetic and review was skipped, while its summary still reads "Verification: passed."

**Where this is bad for Circuit:** "Routing" is the weakest word in the vocabulary here: the router records, it does not decide, and routed_by/router_reason are constants. Circuit cannot fall back on capability either: model-isolated, it fixes the same number of bugs as the bare agent (0.50 = 0.50). The one thing it owns is a lower false-fix rate (0.500 to 0.333), which is honesty, not intelligence and not routing. And the only committed full-loop receipt is a synthetic fixture whose operator summary says "Verification: passed" while its own reports disagree on the outcome.

**Class / confidence:** confirmed / high

### WI-3 - Is the graph-runner enforcement a real capability gap a disciplined CLAUDE.md cannot replicate?

**Steelman of the concern:** A CLAUDE.md is a prompt: instructions the model follows on its honor. The model decides whether to retry, how many times, whether to re-enter a step, and whether to stop. Circuit's graph-runner moves all of those out of the model's discretion into a deterministic loop the model cannot reach: maxAttempts is a coded integer enforced at step entry and route selection, an undeclared route is a hard abort, and retry-with-feedback hard-throws unless the retry route provably targets the same step. A state machine cannot be sweet-talked. So this IS a real capability gap, and the "thin wrapper" prior is wrong about the engine.

**Sober verdict:** The four mechanisms are real, deterministic, and engine-enforced, not prompt text. maxAttempts is coded (`src/runtime/run/graph-runner.ts:174-185`) and enforced at entry (`graph-runner.ts:458-488`); undeclared routes hard-abort (`src/runtime/run/run-transition.ts:41-46`); self-pass and completed-step re-entry are distinct coded cycle aborts (`run-transition.ts:82-107`); retry-with-feedback hard-throws unless the retry route targets the same step (`src/runtime/executors/relay.ts:860-890`) under a typed failure policy that defaults to hard-fail (`src/schemas/acceptance-criteria.ts:40-52`). None of the four can be replicated as enforcement by a prompt: a prompt can ask, but compliance is the model's discretion. The "thin wrapper" prior is wrong about this layer. The honest caveat is scope: this enforcement governs Circuit's own internal step graph, not the worker's edits or correctness. The measured payoff is honesty, not capability (`docs/evals/theses-and-hypotheses.md:40-46`), and the control-flow machinery is the structural mechanism that produces it.

**Where this is bad for Circuit:** Genuinely a strength, with two honest limits. The gap is real but narrow: it disciplines the loop (retry counts, route legality, same-step re-entry), not the diagnosis. The engine can perfectly bound how many times it re-runs a relay and still let the model produce a wrong fix on attempt one. And the payoff the enforcement buys is the small, model-confounded honesty margin (0.500 to 0.333) that lives elsewhere in the audit, so "the real product, not the vocabulary" is true for the mechanism while the demonstrated value of the mechanism stays thin.

**Class / confidence:** supported / high

## How it works (HW-*)

### HW-1 - Does the operator digest silently swallow a skipped independent review?

**Steelman of the concern:** A user who runs Fix and lands on the operator summary reads five lines: a headline, an assessment that the fix was applied, "Worker access," "Verification: passed.", and a "Next:" line. Nothing tells them the independent review never ran. Yet the machine-readable report records outcome "partial", review_status "skipped", and a reason naming the reviewer connector failure, and the run still closed "complete." The whole pitch is honesty, so a digest that silently swallows a bypassed adversarial check while reading clean is precisely the failure mode the product claims to prevent.

**Sober verdict:** The contradiction is real and is genuine engine output, not a fixture quirk. The capture script copies the engine-written summary (`scripts/release/capture-golden-run-proofs.ts:908`) and injects the reviewer failure by having no fix-review branch so the relay throws (`capture-golden-run-proofs.ts:467`), producing the real `relay.failed` (`trace.ndjson:62`) and a "complete" close (`trace.ndjson:67`). The data layer is honest (`fix-result.json:1`) but all three prose surfaces show only "Verification: passed." (`operator-summary.md:1`; run-surface "Done: fix completed..." at `run-surface.md:2`). Root cause in source: `buildFixDetails` emits a "Review:" line only when review_verdict is defined (`src/shared/operator-summary/projections.ts:170`), and the schema forbids review_verdict on a skip (`src/flows/fix/reports.ts:898`), so the line is structurally omitted; `caveatsFrom` only harvests Confidence/Residual/Fold-in/Consider details (`src/app/operator-summary/writer.ts:413`), none of which a skip produces, so no caveat appears either.

**Where this is bad for Circuit:** When the independent review is bypassed, the operator's 30-second digest reads as a clean pass and states nothing about the audit being skipped. The honest signal exists in `fix-result.json` but is dropped on the way to every prose surface a human lands on, and the run-level outcome is laundered from "partial" to "complete." For a product whose entire pitch is "we don't fabricate a clean result," a headline that omits a skipped adversarial check is the worst possible place to lose fidelity, and the omission is structural, not a one-off typo.

**Class / confidence:** confirmed / high

### HW-2 - Is containment a real git diff against a captured baseline, or a worker-list echo?

**Steelman of the concern:** The only committed Fix proof shows baseline and head SHAs both all-zeros, declared and observed both `["src/login.ts"]`, every diff bucket empty, and a baseline snapshot with `entries:[]`. That artifact is byte-for-byte consistent with an engine that never ran git and merely echoed a worker-declared list back as "observed." The whole run is explicitly synthetic, so a reader has zero firsthand evidence in the shipped proofs that the engine ever shells out to git, captures a real baseline SHA, and re-diffs HEAD.

**Sober verdict:** The mechanism in source genuinely diffs git, not worker self-report. The helper shells out to `git rev-parse HEAD` (`src/shared/git-state.ts:84`), `git status --porcelain` (`git-state.ts:94`), and per-path `git hash-object` (`git-state.ts:138`). The observed set is computed entirely from the two git snapshots (`src/shared/runtime-touched-files.ts:116`), and the worker's declared list enters only as corroboration, never to compute observed (`runtime-touched-files.ts:155`); the change-set status flips to 'fail' on parity break, HEAD divergence, or hidden index flags (`src/flows/fix/writers/change-set-projection.ts:47`). So against raw self-report (no ground truth at all), this is a categorical improvement. But two caveats: enforcement is a soft downgrade, not a hard stop. A 'fail' change-set only denies the 'fixed' label and drops outcome to 'partial' (`src/flows/fix/writers/result-projection.ts:70`); the out-of-scope write still lands. And the only committed Fix proof is the synthetic all-zeros fixture (`change-set.json:4`; `baseline-snapshot.json:3`; `brief.json:5`) that never exercises the live git path.

**Where this is bad for Circuit:** The premise is correct about the artifact: the only Fix proof is a synthetic fixture that never runs git, so its declared==observed parity is vacuous and would look identical with or without a real diff. There is no committed live proof of the containment firing on a real out-of-scope edit. And even when the live mechanism fires, it is detection-after-the-fact, not prevention: nothing physically stops the disallowed write because Circuit imposes no OS sandbox on a write-capable worker.

**Class / confidence:** supported / high

### HW-3 - Is close_allowed a binding completion gate or advisory?

**Steelman of the concern:** Read naively the proof looks like the feared failure: the fix-act step records overall_status 'weak' and close_allowed:false, yet the run later closes "complete." If close_allowed were a single global "may this run close" flag, then closing complete over a step that just voted false would mean the engine stepped past a no-vote because some later proof was green: the exact "model self-declares done, gate is decorative" pattern.

**Sober verdict:** close_allowed is binding, but conditionally, and the trace is a true-positive of the design, not a bypass. The lever is the per-proof flag close_requires_proven, computed identically by both executors as `closeAllowed || stepCanCloseRun(step)` (`src/runtime/executors/relay.ts:208`; `src/runtime/executors/verification.ts:152`), where stepCanCloseRun is true only if the step declares a terminal route to @complete (`src/runtime/executors/shared.ts:44-47`). The weak fix-act proof carries close_requires_proven:false (`trace.ndjson:idx40-41`), so its no-vote is advisory by construction; the fix-verify proof carries close_requires_proven:true and passed (`trace.ndjson:idx47-48`). At close, `completeCloseProofGap` considers only guidance with close_requires_proven===true and demands a later matching proof that is proven and close_allowed (`src/runtime/run/run-close.ts:110-133`), then downgrades 'complete' to 'aborted' on any gap (`run-close.ts:143-144`). A schema superRefine independently rejects close_allowed:true while overall_status!=='proven' (`src/schemas/trace-entry.ts:667-672`). So the run closed complete only because the one close-binding proof was proven; the gate is real and double-checked.

**Where this is bad for Circuit:** "close_allowed:false is a binding gate" overstates what the flag alone does: whether a false vote binds depends entirely on close_requires_proven, which is driven by close-capability, not by how serious the no-vote is. A weak act-proof's false vote is advisory by design and is genuinely stepped past, exactly the surface behavior the question flags. It is only not a bypass because a separate close-capable proof passed. And damning for evidentiary weight: in this synthetic fixture that binding proof was a `node -e process.exit(0)`, the change SHAs are all-zeros, and the fix-review relay actually failed (`trace.ndjson:idx61`) yet was routed past. The wiring is real and code-enforced; the evidence it consumed here is hollow.

**Class / confidence:** confirmed / high

## Value and cost (V-*)

### V-1 - Is the model-fair honesty win generalizable, or one discriminating task dressed as a rate at n=12?

**Steelman of the concern:** The only model-isolated comparison is 4 tasks x 3 reps = 12 paired observations, and two of those tasks are degenerate (fixed 0/3 by every config including direct Haiku), carrying zero information. The entire delta lives in two cells: wrap-index and fit-width, a swing of exactly two false-claims-flipped-to-honest-failures. "0.500 to 0.333" sounds like a rate but is "2 fewer false fixes out of 12," concentrated in one over-calibrated task and one model-trap. At ~3% power no CI would exclude zero, and the very next default-on run shows vanilla false-fixing 0/12 on the same tasks, which would erase the gap entirely.

**Sober verdict:** Read firsthand, the structure control shows Circuit false-fixed 0.333 vs vanilla 0.500 at equal objective-fixed 0.50, n=12 (`docs/audits/2026-06-11-eval-heldout-hardening.md:294-300`). The delta is not wrap-index alone: wrap-index reads 3/0 vs 2/0 and fit-width 3/0 vs 2/0 (`audit:313-318`), two flips across two tasks while the trivial tasks tie at 0/3. The artifacts do not claim the effect holds at 25-40 tasks; they claim the opposite about the present run. The charter states the 4-task suite "cannot reach significance under any outcome" and needs ~25-40 discriminating tasks (`docs/evals/theses-and-hypotheses.md:381-384`), binds reporting to "claim direction, not magnitude" (`theses:400-406`), grades H1a "supported (at Haiku)" not confirmed, leaves Sonnet/Opus generalization untested, and the rival null open (`theses:124-139`). The committed pin_model control confirms the numbers (`evals/ledger/fix-vs-vanilla/2026-06-11T22-27-58-442Z-...json`), and the next-day run logs vanilla false-fixed 0 on the same set (`...2026-06-12T15-49-10-758Z-...json`).

**Where this is bad for Circuit:** The headline structure-isolated honesty win rests on two flipped cells out of twelve, on a suite the project's own charter says has ~3% power and cannot reach significance under any outcome. No CI excluding zero exists, the data is demonstrably noisy (the next run erases the gap), and the win has never been tested at Sonnet or Opus, the models actual users run. As of now "more honest, not smarter" is a direction with one or two data points behind it, not a measured, generalizable effect.

**Class / confidence:** supported / high

### V-2 - Is the per-task dollar cost of the trustworthiness win known, bounded, and disclosed before the run?

**Steelman of the concern:** Trustworthiness is bought with extra model calls, so an operator must be able to answer "how much more does this cost per task, and do I see it before I commit?" On both halves the artifacts fall short: there is no committed dollar ratio versus raw Claude Code at the shipped medium default (the one run that captured Circuit dollars logged the vanilla arm usage-missing 12/12), the charter still says dollars are not recorded, and the only dollar figure that ever reaches a human is a post-hoc receipt built after every relay has spent.

**Sober verdict:** Two premises hold, one is now partly stale. A committed Circuit per-fix figure exists at the shipped medium default: $6.7518 over 12 tasks, ~$0.56/fix, with descriptors circuit_power "default" and pin_model "false" (`evals/ledger/fix-vs-vanilla/2026-06-12T15-49-10-758Z-...json:34`, :12). The harness confirms pin_model false means relays ran on the default-on-medium stack, and the model field labels the host base model (`evals/fix-vs-vanilla/run-fix-comparison.ts:773`). So the charter line "Wallclock is recorded; tokens and dollars are not" (`docs/evals/theses-and-hypotheses.md:297`) is stale for the Circuit arm. But the comparator is genuinely empty: vanilla_usage_missing_count 12 (`ledger:37`), so no dollar multiple exists. The only committed comparative cost fact is wallclock, ~3.2x (`ledger:26`). And the price an operator sees is a post-run receipt accumulated from relay.completed entries (`src/app/operator-summary/writer.ts:728`, :876), not a pre-run estimate; README has no cost mention at all.

**Where this is bad for Circuit:** At the shipped medium default there is no committed, disclosed dollar multiple versus raw Claude Code, and no price shown before the run. The absolute Circuit figure (~$0.56/fix) is honest about the shipped config, but the vanilla arm's cost was lost to the envelope bug, so the trustworthiness comparison and the cost comparison were never captured in the same usable run. The charter doc still asserts dollars are not recorded, contradicting the now-committed Circuit figure: the project's own description of its cost instrumentation is internally inconsistent. And the only price an operator ever sees is printed after the money is spent.

**Class / confidence:** supported / high

### V-3 - Is Circuit's value in the harness, or one opus-diagnosis habit a strong engineer can hand-roll?

**Steelman of the concern:** The dial sweep is unambiguous: low/medium/high all land identical 0.25/0.75, and the one shared ingredient is an opus researcher. Circuit's own thesis concedes that once the cause is known "the fix is often a one-liner any model can write." If the entire lever is "diagnose root cause with a strong model first," that is a prompt-shaped habit: a competent engineer can write `claude --model opus "diagnose root cause first, then fix minimally, then run my verify script"` and capture most of the gain for one opus call, while Circuit charges the whole multi-role pipeline and runs ~3.5x slower.

**Sober verdict:** The dial-sweep facts hold and are by Circuit's own T3 design (`docs/audits/2026-06-11-eval-heldout-hardening.md:280-287`; `docs/evals/theses-and-hypotheses.md:48-53`). So the capability delta is a diagnosis-tier effect a strong-model prompt could reach. But the question's framing is not the whole claim: the model-isolated structure control pins both arms to Haiku (no opus anywhere) and still cuts false-fixed 0.500 to 0.333 at equal objective-fixed 0.50 (`audit:294-307`). That delta cannot be the opus habit, since there is no opus in the run; it is structure making the agent more honest (`theses:40-46`). The catch: that honesty edge is thin (only wrap-index strongly discriminates; the Haiku-pinned win rests on it alone, `audit:207-210`, :317), and the verify-step half of the named baseline supplies exactly the external hidden check T4 says drives the result (`theses:55-60`). So the harness is not the only path: it is a packaging of two habits (opus-first diagnosis + external verification) into a default that fires without discipline.

**Where this is bad for Circuit:** On the only quantitative evidence, the capability portion is genuinely prompt-shapeable: the dial sweep proves implement/review tiers buy nothing, and T3 concedes it. The structure-only honesty edge that survives model isolation rests on a single discriminating task across a 4x3 set, and Circuit charges ~3.5x wallclock plus a multi-role bill for it with no committed token/dollar ratio to justify the overhead. A sharp engineer with a shell-script verify gate and an opus-first prompt can replicate the bulk of both halves for far less. Circuit's honest differentiator is narrow: it makes the habit fire by default without operator discipline, not that the habit is impossible to hand-roll.

**Class / confidence:** supported / high

### V-4 - Does the flow add honesty over raw Claude Code on the same default medium stack it ships?

**Steelman of the concern:** The marquee "25% vs 58%" compares opus/sonnet-stacked Circuit against single-shot Haiku vanilla: a model comparison, not a structure one. When the model is held constant (both Haiku) the gap collapses to 0.333 vs 0.500 at n=12, and the audit concedes roughly half the confounded headline gap was just stronger models. The one task carrying the residual signal is wrap-index, which Circuit still false-claims 2/3 at pinned Haiku. So the value proposition a team actually faces (does the flow add honesty over raw Claude Code on the same default models) is unproven at the models real users run: H1b is "untested" and the rival "structure is a weak-model crutch" is live.

**Sober verdict:** The audit is candid and the notes check out. The headline is confounded (`docs/audits/2026-06-11-eval-heldout-hardening.md:165-168`), and the author says do not cite it as flow evidence (`audit:254-258`). The clean structure control pins both arms to Haiku and shows 0.500 to 0.333 at identical 0.50 objective (`audit:295-307`), which is honesty-not-intelligence (`docs/evals/theses-and-hypotheses.md:142-146`). But that control is at Haiku, not the default medium stack the question asks about. The medium-stack-vs-raw-Claude comparison does not exist anywhere in these artifacts: the only same-model control is Haiku, and the Sonnet control (H1b) is marked the untested next experiment (`theses:128-133`). The residual effect is fragile (0.167 absolute at n=12, concentrated in wrap-index, `audit:333-342`), and there is no committed token/dollar multiple, only ~3.5x wallclock (`theses:297-300`).

**Where this is bad for Circuit:** The specific comparison the question demands (flow honesty added over raw Claude Code on Circuit's own default medium stack) has never been run. The only same-model control is at Haiku, a model the audit itself says real users do not run, and even there the effect is 0.167 absolute at n=12 resting on a single task, while a second task defeats the structure entirely (all-opus included). The audit names the rival H1c outright: the gap may be only a weak-model crutch that vanishes at Sonnet/Opus, shrinking the value to "run a cheaper model and stay safe." So at the default models a team would use, the flow's marginal honesty over raw Claude Code is currently unknown.

**Class / confidence:** blocked / high - to resolve: run raw Claude Code vs Circuit Fix with both arms force-pinned to the shipped default medium stack (researcher opus, implementer/reviewer sonnet) on the held-out set at K=3+, using the force-override wrapper so the dial cannot inject a per-role model, with committed token/dollar capture; a larger implementer/reviewer-stressing held-out set is also needed to confirm the effect is not a single-task artifact.

### V-5 - Does Build measurably cut regressions or scope-drift vs raw Claude Code with subagents on real multi-file work?

**Steelman of the concern:** T6 is the single thesis that would justify Circuit for strong engineers on the hard work they want help with. If that interaction is never measured, the "Build helps on big work" pitch rests on an untested prediction, and the dial sweep gives real reason to fear the curve is flat. Worse, the named baseline (raw Claude Code orchestrating its own subagents) has never been run at all, even on small tasks; the only comparison instantiated is single-shot direct Claude. So the capability claim on larger work is not merely unproven, it lacks the instrument and the right baseline to be proven.

**Sober verdict:** The larger-work capability claim is entirely unproven, and the repo says so. T6, H6a, H6b are all marked untested, and the instrument (the Build complexity ladder) is explicitly noted as not existing (`docs/evals/theses-and-hypotheses.md:176-177`, :338-339). Every committed eval task is single-file Fix-flow work (`evals/fix-vs-vanilla/tasks/heldout-wrap-index/task.json:11`), and the registry registers only fix/auto/review/handoff (`evals/registry.json:7`). The measured small-fix capability gap is zero (`docs/audits/2026-06-11-eval-heldout-hardening.md:300-307`), and the dial sweep is flat with only the researcher mattering (`audit:270-288`), which is direct evidence against the implement/review tiers carrying capability weight, exactly the lever T6 would need. The vanilla arm is a strong direct agent prompt, not orchestrated subagents (`evals/fix-vs-vanilla/README.md:6`), so even the small-task comparison never tests the named baseline.

**Where this is bad for Circuit:** The capability advantage of Build on larger multi-file work is completely unproven: zero eval evidence, no instrument, no Build flow ever benchmarked, every committed task a single-file fix. The available signal points the wrong way: the flat dial sweep is direct evidence the implement/review structure adds no capability even at higher tiers, and the model-isolated control shows the flow buys honesty, not correctness. The comparison strong engineers care about (Circuit Build vs Claude Code orchestrating its own subagents on multi-file work) has never run against that baseline even once. The repo's own thesis states the risk: if the curve is flat everywhere, Build's capability pitch is wrong.

**Class / confidence:** blocked / high - to resolve: build the complexity ladder instrument (graded single-function to cross-cutting tasks, each with hidden adjacent-regression checks and diff_scope tracking, rungs assigned before any arm runs), then run three arms up the ladder at a fixed model (Circuit Build, single-shot direct Claude, and Claude Code orchestrating its own subagents), reporting objective pass, hidden regression rate, and diff_scope per rung; T6 confirms only if the Circuit-minus-baseline gap is ~zero at the bottom and positive at the top.

## Who it is for (WF-*)

### WF-1 - Is the honesty win redundant for a strong engineer who already verifies by hand?

**Steelman of the concern:** The only proven effect is that the agent over-claims less. But the entire value of "fewer false fixes" is to spare a user the cost of trusting a fix that is secretly broken. A strong, already-skeptical engineer running raw Claude Code captures that value for free the moment they read the diff and run the test, which the persona stipulates they do. ### WF-2 - Is the worker boundary enforcement, or convention?

**Steelman of the concern:** If you read Circuit's own docs honestly, the worker boundary is convention, not enforcement. The README states `capabilities.filesystem: read-only` is "a routing signal, not an OS sandbox," and a write-capable worker inherits the Circuit process environment and cwd with no write restriction. The lone hard containment, allowed_touch_area, is Build-only, opt-in, and inert when undeclared, and even when it fires it does not prevent the bad write: the edit already happened; the engine only refuses to label the run complete. For untrusted or junior work on a shared checkout, that is a security-relevant gap.

**Sober verdict:** The concern is essentially correct and Circuit says so itself. read-only is a routing signal that only refuses to assign a read-only connector to an implementer role (`src/connectors/resolver.ts:113-119`); it does not sandbox a write-capable worker (`README.md:131-134`). The claude-code connector imposes no filesystem restriction and comments "Tools are unrestricted by design" (`src/connectors/claude-code.ts:284`). allowed_touch_area is Build-only and opt-in (`src/flows/build/writers/baseline-snapshot.ts:41-49`), and when undeclared the writer emits not_enforced and runs no git (`src/flows/build/writers/touch-area-projection.ts:46-57`). Even when declared it is a post-hoc git diff that downgrades the outcome rather than preventing the write. The one genuine OS boundary is not Circuit's: it is Codex's own CLI sandbox via frozen `-s workspace-write` (`src/connectors/codex.ts:24-33`), preserved by a forbidden-argv guard, and it covers only the Codex worker.

**Where this is bad for Circuit:** Circuit imposes no OS-level filesystem isolation on its primary write-capable workers; they inherit the parent cwd and environment and can write anywhere those permit. The single structural gate is Build-only, off by default, and even when on lets the write happen and then refuses to mark the run complete: a soft outcome-downgrade, not containment. For untrusted or junior-engineer agents on a shared checkout, Circuit is not a substitute for a container or OS sandbox, and the read-only disclosure plus the one-line worker-access notice are convention, not enforcement.

**Class / confidence:** confirmed / high
