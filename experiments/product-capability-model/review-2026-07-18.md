# Capability model review, 2026-07-18

Adversarially verified review of `catalog.json`. Method: one verifier per
capability (31), six gap-sweep lenses (CLI surface, engine runtime,
multi-host, roadmap docs, release claims, model structure), and an
independent refuter for every medium or high finding. 110 agents total.
Findings that did not survive refutation were dropped (3 candidates, plus
several per-entry claims). Full structured findings with file evidence:
[`review-findings-2026-07-18.json`](./review-findings-2026-07-18.json).

## Verdict

The model's shape works. The seven areas held up, capability grain stayed
stable across 31 entries, and the review could name real product decisions
from the catalog alone. That is the spike's pass condition.

The content does not yet deserve trust. The mechanical audit is green
(15/15 commands, 13/13 flows, 29/29 blocks) while 18 of 31 entries carry at
least one confirmed inaccuracy. Only the five work-pattern entries and
frame-work came through fully clean. The errors are not random. They fall
into four systematic patterns, each pointing at a check the permanent
version needs.

More important than the inaccuracies: the catalog under-sells the product.
The sweeps found roughly a dozen shipped capabilities with no catalog home,
including several that carry the launch messaging (multi-host operation,
the engine-enforced honesty floor, live progress streaming, ambient
continuity).

## Part 1 — Accuracy: four systematic patterns

### Pattern A: exposure is asserted, never derived (worst offender)

Exposure is the catalog's most user-facing claim and nothing checks it.
Confirmed errors:

- **iterate-until-proof says `mixed`; the truth is `internal`** (high).
  Both mapped flows (converge-proof, fix-until-green) are
  `visibility: 'internal'`, the goal-attempt/goal-evaluate blocks live in
  the internal goal flow, and no public flow opts into the until-loop.
  This directly contradicts `docs/positioning.md` claim 4, which orders:
  "do not present a public 'converge' command as existing today." A
  catalog that outranks positioning on optimism is a public-claims risk.
- **cross-session-handoff says `public-host`; should be `mixed`.** Handoff
  is a host slash command AND a top-level CLI command AND its block runs
  in the public fix flow. Identical shape to route-intent, which earns
  `mixed`. Same facts, different value.
- **allocate-step-equipment says `mixed`** but neither listed surface is
  host-reachable: preview is CLI-only and cross-tool-build is internal.
- **encode-typed-flow says `public-cli`** while mapping zero commands and
  only the internal explainer flow. The actual public encode path
  (create/generate) is mapped to manage-custom-flows. Either the exposure
  or the surface list is wrong as written.
- **reuse-run-evidence says `public-cli`; should be `mixed`** (see
  Pattern D: run-start recall runs inside every hosted `circuit run`).

Fix direction: make exposure derivable, or at least checkable, from a
host-publication inventory (which commands and flows each host actually
ships) joined against mapped surfaces. The model has the roster; the audit
never consults it.

### Pattern B: proof refs do not prove what they claim (8+ entries)

`tests/runner/flow-facts.test.ts` (a 77-line authoring-parity test that
never executes a flow) is cited as behavior proof by own-bounded-outcome,
queue-batch-work, recover-cleanly, independent-judgment, and frame-work.
bounded-composition and configure-circuit cite contract tests that never
touch the claimed behavior. deterministic-checks' refs prove step
expansion, not check execution. My own spot-check adds role-shaped-steps:
`runtime-context-boundary.test.ts` asserts architecture import boundaries,
not per-step context scoping.

The strength labels are wrong in both directions:

- **Overstated:** preview-execution claims `release-proof` but `preview`
  appears nowhere in `generated/release/current-capabilities.json` and no
  golden-run scenario exercises it. iterate-until-proof's `release-proof`
  has zero until-loop records in the release inventory. (The spike never
  defines `release-proof`; that is part of the problem.)
- **Understated:** manage-custom-flows says `source` while a full
  create → publish → run e2e exists in `tests/runner/utility-cli.test.ts`
  plus 8 generate cases. check-readiness and maintain-installation have
  dedicated behavior suites their entries never mention.

In almost every case the right test exists in the repo and simply is not
the one cited (goal-flow.test.ts, pursue-runtime-wiring.test.ts,
until-loop-runtime.test.ts, doctor runner suite). A reviewer who trusts
the refs would rank strong capabilities as unproven and weak claims as
release-attested. Fix direction: define the strength rungs, and require
that at least one ref demonstrably exercises the claimed behavior.

### Pattern C: the every-flow/block-mapped rule backfires

The audit forces every flow and block into some capability's `surfaces`
list, and `surfaces` has no visibility marker. Consequences:

- Internal proof flows masquerade as product surface: runtime-proof
  (under role-shaped-steps and bounded-composition), explainer (under
  encode-typed-flow), cross-tool-build (under allocate-step-equipment).
- explainer is mapped to a capability it does not deliver. It is a craft
  flow (paper → interactive explainer) parked under encode-typed-flow
  purely to satisfy the rule, which simultaneously misstates
  encode-typed-flow's surface and makes explainer's real purpose (craft
  artifacts for humans, a second flow class) invisible.
- Never-executed blocks read as delivery: intake and route appear under
  route-intent, but no schematic uses them and routing is model-only per
  `src/commands/run.md`. Same for queue (queue-batch-work) and
  risk-rollback-check (recover-cleanly, which is marked `shipped` with no
  note). A reader could scope routing work as "wire in the existing
  blocks" when those blocks have never run.

Fix direction: add a visibility/dormancy marker to surface entries, or
split "product surface" from "proof surface." The queue-batch-work entry
already models the honest pattern (internal exposure plus boundary note);
it just is not enforced.

### Pattern D: stale or wrong prose in summaries and attention notes

- **resume-work's summary overpromises (high).** It claims resume after
  "checkpoint, interruption, or host restart." Truth: resume works only
  from a declared checkpoint. A run interrupted mid-flight exits 2 with a
  pointer to `circuit runs show`; crash recovery is the unmerged
  durability workstream; `--reuse-children-from` starts a fresh run. A
  reader could deprioritize crash-durability work because the catalog says
  interruption recovery already shipped.
- **own-bounded-outcome's note presents Goal-vs-Pursue as fully open.**
  A decision is already recorded in source: Goal is frozen internal (S8),
  its contract/gate semantics moved into the Run envelope (Phase 13). The
  remaining open question is only Pursue's product shape. The catalog's
  first standing review question is partially answered and does not know
  it.
- **inspect-runs' gap note is wrong by omission**: "reconnectable
  watching ... not shipped" erases the live `--progress jsonl` channel
  that IS shipped (see Part 2).
- **fanout-compare misses explore**: the public explore flow's decision
  tournament (proposal-fanout-step, execution kind `fanout`, dedicated
  tournament schemas) delivers exactly this capability; surfaces list only
  prototype. The `--tournament [2|3|4]` run flag is unmapped too.
- **reuse-run-evidence lists only `history`** while its primary delivery
  is automatic run-start recall inside every real `circuit run`, on by
  default. Its own proof test exercises the run command.

## Part 2 — Gaps: shipped capabilities with no catalog home

Ordered roughly by product weight. All verified against source by two
independent agents.

1. **Multi-host operation.** Same encoded flows from two hosts with
   mirrored surfaces (both plugins: run + handoff + the same five public
   flows). Host identity is behavioral: `HostKind` is a schema enum,
   connector auto-resolution branches on it, doctor threads it. A headline
   promise ("your process is portable across agent tools") with zero
   catalog representation; "codex" appears nowhere.
2. **Engine-enforced evidence integrity.** The honesty-floor machinery:
   overclaim latches that make a clean `complete` impossible
   (honesty-ledger), frozen-eval fingerprinting ("a tampered run can only
   end needs-attention"), stop-judge disposal against an independent
   evidence floor, terminal-outcome binding. The catalog attributes
   honesty entirely to worker-side close blocks; the engine-side
   enforcement that makes it a guarantee, and that carries the launch
   messaging, is invisible.
3. **Ambient continuity capture.** Zero-setup Stop/SessionEnd/PreCompact
   harvest, a first-class `continuity_kind: 'ambient'` in the contract
   with its own pointer and resolver precedence. Folded illegibly into
   cross-session-handoff, whose summary describes only the deliberate act.
   Also host-asymmetric (Codex is restore-only, install-gated), which the
   exposure taxonomy cannot express.
4. **Follow a run live.** `--progress jsonl` on five commands,
   schema-validated events, per-flow progress surfaces, and the Claude
   wrapper auto-injects and renders it today. The catalog's only trace is
   an attention note claiming watching is not shipped.
5. **Skill Hooks.** Signal-driven injection of operator skills into
   implementer relays (`before:edit-files:.ts`, `after:verification-failed`),
   contract-pinned and tested. Direct encode-process + fit-work-to-step
   capability; wholly absent.
6. **Autonomous unattended operation.** `--autonomous` bounded
   continuation loop with recovery routing and "never closes complete by
   exhaustion." The inverse of operator-decisions and its natural sibling.
7. **Depth and Power dials.** `--power` (with auto tier + provenance) and
   `--process` gate model spend and process rigor per run. Selection
   behavior, not configuration; unmapped.
8. **Measure whether a lesson helped.** `history memory-effect`,
   `memory-merge`, and measured-negative suppression are shipped. The
   learning area currently claims the loop is entirely proposed, which
   understates the shipped half of the catalog's own future-loop pillar.
9. **Spend governance.** Fail-closed USD/token caps on until-loops plus
   per-role spend in the operator summary.
10. **Bounded mid-run adaptation.** Equipment reshape (budgeted skill-slot
    injection) and typed context pull-then-retry. Internal, but a real
    differentiator against the bounded-dynamism boundary.
11. **Close-out artifacts for humans.** Operator summary (md + HTML), run
    surface, decision packets. honest-close covers the verdict, not the
    human-readable explanation layer.
12. **Orientation and discovery.** Bare `circuit` (TTY shell / piped
    static page) and the guided help system. Outside the 15-command
    vocabulary, so the audit cannot see it.
13. **Custom connector extensibility** (release-attested, documented) and
    **install/first-run onboarding** (the launch plan's announce bar;
    removal is cataloged, install is not).

Missing proposed capability: **watch, answer, and safely cancel a live
run** (durable Run handle, `circuit now`). It is committed and canonical
(run-milestone-stream.md decision, launch-plan deferred list,
cli-first-principles held plan), exactly the bar improve-flows-from-evidence
met to earn its proposed row.

Missing boundaries (all settled in committed docs, same class as the four
already listed):

- Memory guides, never governs: hint-only, cited, no authority over
  routes/checkpoints/proofs, no "Circuit learns" claim until measured
  effect earns it. This is the load-bearing fence around the one proposed
  capability in the catalog.
- No universal progress percentage, no invented ETA.
- No generic pause button, no free-form mid-worker steering.
- Hosts never become the orchestrator (host-managed workers rejected).

## Part 3 — Structural opportunities

- **route-intent's graph edge is arbitrary.** Its only edge is "enables
  audit-work" while the reason names the whole work-pattern fan-out; the
  other four work patterns have no incoming edge at all. The rendered map
  literally says Run routes only to audits. Either five sibling edges or
  allow area-targeted edges.
- **All three `extends` edges are direction-inverted** relative to their
  own reason text ("fan-out adds branches to the authored graph" means
  fanout extends composition, not the reverse). The generated table
  renders the backwards sentence verbatim.
- **The exposure taxonomy cannot express per-host reach.** Harmless today
  (the public surface is host-symmetric) but it bites exactly where the
  catalog's known gaps are: ambient capture is public-on-Claude,
  absent-on-Codex, and the schema cannot say so.
- **Review question 3 tags the wrong pair** (own-bounded-outcome +
  queue-batch-work invites a false Goal-vs-Pursue = capability-vs-capability
  reading; both flows live under own-bounded-outcome). And per Part 1D the
  question is already half-answered in source.
- **preview-execution is the only attention-flagged capability with no
  review question.** The real open question: should Circuit compute
  dependable per-run time/cost estimates, or does cost candor stay static
  documentation?
- **cross-session-handoff is orphaned** from the continuity cluster's
  relationships and from review question 5, which names the continuation
  story it exists to serve.

## What this means for the spike decision

Against the README's own keep/kill questions: the catalog let a review
find real gaps, real overlaps, and real decisions faster than touring the
repo would have. Grain held at 31. Keep it.

But the green mechanical audit currently certifies a map whose most
important claims (exposure, proof strength) are wrong in 18 entries. The
promotion path should add, in roughly this order:

1. A host-publication inventory so exposure is derived or checked, not
   asserted (kills Pattern A).
2. Defined proof-strength rungs plus a "ref must exercise the behavior"
   rule (kills Pattern B; `release-proof` needs a definition to exist).
3. A visibility marker on surface entries, or a separate proof-surface
   slot, so internal flows and dormant blocks stop reading as product
   (kills Pattern C).
4. An intake pass over Part 2 before the catalog is used for any real
   prioritization: as it stands the model would systematically steer
   investment away from the engine's differentiators, because the things
   the engine does best are the things the catalog cannot see.
